Editing my website directly in my browser

 01 Jan 1970 · 1 min read

This website is editable.

If you add ?edit to the URL of any page on this site, it will activate edit mode.

You can't save it of course; you don't have access to my files. But I can via the Web's File System API. I'm able to edit my site via my site.

In fact, the text on this article was primarily written using this page!

But why?

Mainly for fun, but this was a long time goal of mine ever since I rewrote my site in vanilla HTML.

When I rewrote my site in vanilla HTML, build step was gone. The build step was the main blocker from having the HTML editable since you have to unbuild it to save it back.

The HTML file could become the authoring platform, in addition to being the publishing medium as well as the coding medium..

(diagram)

I'm going back to basics on this one.

CMS -> the file system
Frontmatter -> read data already in markup, <meta>, <title>, <time>
✌️“WYSIWYG”✌️ editor -> HTML page + ?editt
Advanced editor -> HTML source
Widgets -> JS

That in itself doesn't mean anything for you readers, but it would make my writing experience much smoother. My thoughts could flow directly into the page unhindered. I already felt some freedom when I removed my build step and added live reload, because the feedback loop was much faster. Now, writing directly in the page eliminates the feedback loop at all. No more switching between multiple applications.

Content Editable

I turns out, browsers support editing HTML natively via the contenteditable attribute. Just set this on any element and it becomes editable.

Formatting options are lacking though, and browser implementations are different. I I can always go back to my code editor.

With contenteditable, the browser is doing the heavy lifting. However, that's not all of it.

DOM vs Source

When I said no build step I lied. Well, not really. You see, there's still an inherent compilation step that is happening inside the browser. This is parsing the HTML into the DOM. What you actually see and interact with is the DOM.

(diagram of actual predicament)

Editing within the page means editing the DOM, not the source itself. Going from DOM to source is much harderd than converting source to DOM.

Just saving body.innerHTML into a file won't work, because it would mess up my manual HTML formatting. (Prettier sucks for HTML)

It also will mess up things like dynamic elements (innerHTML saves a snapshot of the DOM), breaking interactive HTML and custom elements.

Reflections

It's not perfect. It's full of edge cases, but I can always fall back to editing the source. The good thing about this is I can switch to either workflow any time because in the end I'm working on the same file.

I first imagined using this for doing the final edits before publishing a post, but I actually can write the whole text of the post this way.

I imagine writing the main text in the browser, then going into the HTML to insert media, mark up code or note boxes and other formatting, and to code interactive sections.
