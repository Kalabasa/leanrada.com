Cool URLs don’t change with snapshot testing

 25 Jan 2026 · 1 min read

I wrote automated tests to keep track of my site’s URLs and prevent links from breaking.

When I reorganised my site, I changed a lot of URLs and broke some inbound links. Now that more and more sites have started linking to my site, I don’t want to inadvertently break links again.

Cool URIs don't changeTim Berners-Lee (1998)

This post is not about how to implement ‘cool URLs’. There are too many ways to do that depending on the site’s setup and the site’s philosophy even. Rather, this post is about ensuring cool URLs, a contract to guarantee live URLs. It doesn’t matter how you fulfill that contract, e.g. redirects, rewrite rules, just that you follow the contract.

There already exists a contract: a social contract when you publish a webpage. Other people can link to your URL on their sites, and you can link to other people’s content on your site in return. It’s the World Wide Web. Unfortunately, URLs often break for various reasons.

Universal web standards allow us to define a stronger contract via automated testing of HTTP and HTML.

Automated testing

So, you have a website that serves a some HTML files over HTTP. It could be a static site, or Java Spring Boot, or PHP, it doesn’t matter.

We can test the website by communicating with it via HTTP, agnostic of the underlying technology. Essentially, the test checks each URL off a list of known URLs and expected responses.

test.each([
  ['/', 200],
  ['/about', 200],
  ['/about/', 200],
  ['/signin', 301, '/login'],
  ['/news', 302, '/en-US/news'],
  ['/api/ping', 204],
  ['/dashboard', 403],
  ['/secret', 404],
])('%s %i', async (path, status, location) => {
  const res = await fetch(base + path, { redirect: 'manual' });
  expect(res.status).toBe(status);
  if (location) expect(res.headers.get('location')).toBe(location);
});

But manually writing a test case for every URL is a pain. A crawler script can help with this by scanning the HTML responses. Still, updating the tests would be tedious.

Snapshot testing

I figured the easiest or most appropriate way to do this is via snapshot testing.

Snapshot testing takes a snapshot of a system’s outputs and compares it with a baseline snapshot (snapped from a previous run). This means I don’t need to manually update the tests. The tests can update themselves.

Here’s how it works: A crawler script would gather all the URLs on the site, saving a snapshot of them in a text file. Some snapshot testing approaches directly insert values in the test code itself, but I prefer a separate artifact for this.

/
/about/
/notes/
/wares/
/wares/pong-ai/
...and so on...

After making refactors or any code changes, I can run the crawler again, and compare the snapshots. If the snapshots change, then some URLs have been changed.

Snapshot testing with git

With git, I don’t actually need to ‘write tests’ or use a testing framework.

git can act as the test harness.

  • The test is failed if git detects changes in the snapshot file.
  • On failures, git diff shows me the expected and actual values, just like a testing framework.
  • To approve changes to the baseline, I commit the snapshot file.

I run the crawler in a git pre-commit hook to abort commits when the snapshot has an unapproved change. The actual test is to check the exit code of git diff.

# pre-commit
node test/url >git-hooks/pre-commit.log 2>&1
if ! git diff --quiet -- test/url/snapshot; then
  echo "URL snapshot file changed. Commit aborted."
  exit 1
fi

With this, any change to URLs must be intentional.

If I wanted to restructure my site again, I can ensure that existing URLs have redirects by looking at the snapshot diff and seeing that no existing URLs have been made unreachable.

As a bonus, this also helps prevent me from accidentally publishing draft posts (which I’ve done a few times)!

Other notes

It’s like Page Indexing tracking in Google Search Console.

The snapshot can be extended to contain more info than a list of URLs.

The status code can be included in the snapshot so it can explicitly keep track of unreachable URLs (which by definition, won’t be crawled).

200 /
200 /about/
200 /notes/
200 /wares/
404 /portfolio/
...and so on...

The crawler can even use the snapshot itself as starting points for the crawl, instead of starting from just the root /. This way, the snapshot does not forget URLs. Once published, a URL is either a 200 or a 404. It’s like bookmarking every page on your site.

This could be extended to track other page properties as well, such as the canonical URL. Anything that is often overlooked or auto-generated that you might want to review before deploying.

What’s the point?

For static plain HTML sites like mine, it’s probably not going to be very useful. URLs change only when you move HTML files around. No surprises here. But since I tend to forget about things and refactor stuff for the fun of it, this will still be a good thing as a self-imposed rule for future me (a contract with myself?).

I have broken the CSS on this site countless times due to CSS refactors. I’ve been meaning to do visual snapshot testing to keep refactors at bay but visual snapshot testing is noisy, not to mention slow. Definitely not a pre-commit thing.

Othe the other hand, for sites made with static site builders, a review of changes to site structure would be good, rather than relying on assumptions about the internal logic of the site generator and manual testing. This is if you’re not already checking in the generated files in source control, at which point the URL snapshot is kinda redundant.

For a complex site with servers, rewrite rules, frameworks, or proxies, a version of this snapshotting routine could be set up to help prevent unwanted changes, but it couldn’t be git-based anymore if you have database-driven or otherwise dynamic URLs.

Client-side route-based sites won’t work at all, unless the crawler is more advanced and can execute JS (hard).

Anyway, this has been too long of a post just to ramble about combining a web crawler sitemap with git.
