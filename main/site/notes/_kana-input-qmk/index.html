How kana works

Kana are syllabaries, writing systems in which a consonant-vowel syllable is written as one character.

A way to type kana on ‘regular’ keyboards is romaji, using Roman letters to output kana symbols. E.g. sushi = すsuしshi.

We can lay it out in a grid with vowels as columns and consonants as rows.

A I U E O
K か き く け こ
S さ し す せ そ
T た ち つ て と
⋮ ⋮ ⋮ ⋮ ⋮ ⋮

This tabular representation inspired the core idea behind my implementation.

The map

The core idea was a 2D lookup table. Since program space is severely limited on a keyboard firmware, I thought it’d be good to represent all of romaji rules in a table.

Columns in the lookup table are the five vowels. But rows include all possible letters in order to generalise the logic, accomodate vowels, and more.

static char MAP[ROW_COUNT][5*3] = {
  // A I U E O
  "あああああ", // A (vowel)
  "ばびぶべぼ", // B
  "？ち？？？", // C
  "だ？づでど", // D
  "えええええ", // E (vowel)
  "？？ふ？？", // F
  "がぎぐげご", // G
  "はひふへほ", // H
  "いいいいい", // I (vowel)
  "？じ？？？", // J
  "かきくけこ", // K
  "らりるれろ", // L
  "まみむめも", // M
  "なにぬねの", // N
  "おおおおお", // O (vowel)
  "ぱぴぷぺぽ", // P
  "？？く？？", // Q
  "らりるれろ", // R
  "さしすせそ", // S
  "た？つてと", // T
  "ううううう", // U (vowel)
  "？？ゔ？？", // V
  "わ？う？を", // W
  "ぁぃぅぇぉ", // X (small vowels)
  "やいゆえよ", // Y
  "ざじずぜぞ", // Z
};

Every Roman letter gets a row in the map even if it doesn’t make sense for kana. This makes the indexing logic simple. Since keycodes are assigned alphabetically in a contiguous block, we can use pointer arithmetic MAP[pressed_keycode - keycode(‘a’)] to look up the row for any letter. The offset is just the letter’s position in the alphabet.

For letter combinations that don’t really make sense in Japanese writing, like he sequence Q,A, let’s mark them with ？ in the map for now. More on special values later.

  "？？く？？", // Q

The X row is reused to input small vowels ぁぃぅぇぉ (there is no ‘x’ consonant in the Japanese language).

  "ぁぃぅぇぉ", // X (small vowels)

Those are the basics of the map lookup design. But you might be wondering how this 2D map of Unicode chars even works in C. What about endianness? Doesn’t Unicode use variable length encoding? How would a 2D table of variable-length characters work?

UTF-8

First of all, the Unicode API of the QMK keyboard firmware framework that I’m using only works with UTF-8, so I’m restricted to that encoding when sending codes from the keyboard to the computer.

UTF-8 is a variable-length encoding spanning the full 21-bit Unicode range U+0000–U+10FFFF. The number of bytes used depends on the character:

Unicode character Bytes in UTF-8
U+0000–U+007F 1
U+0080–U+07FF 2
U+0800–U+FFFF 3

Kana characters are in the U+3040–U+30FF range, falling within the 3-byte range, so any kana character is always 3 bytes in UTF-8.

This means every row in the map, containing 5 kana characters, is consistently 15 bytes long.

Every kana character can then be directly addressable by simple index arithmetic!

// kana_ptr points to the kana character (3 bytes long)
char* kana_ptr = &MAP[letter_index][vowel_index * 3];

Getting a pointer to "すsu", for example, is simply &MAP['s' - 'a'][2 * 3].

Finally, to send a kana character with QMK:

// Get pointer to the kana character
char* kana_ptr = &MAP[letter_index][vowel_index * 3];
// Copy 3 bytes to null-terminated buffer
static char buf[4] = "\0\0\0\0";
strncpy(buf, kana_ptr, 3);
// QMK function to send unicode accepts
// the null-terminated UTF-8 string
send_unicode_string(buf);

Special rules

Romaji doesn’t always neatly map 2 letters to one kana char. For example, the shi in sushi is 1 char: the ‘し’ in すsuしshi. That’s 3 letters to one char.

ch and sh

The main issue is that English sometimes uses 2 letters to represent a single sound. These include the sounds sh and ch. A simple fix is to treat these sounds as proper consonants, and then map raw S,H and C,H key sequences to the virtual consonants. These new rows are appended at the end without affecting the indexing logic of the real letters.

static char MAP[ROW_COUNT][5*3] = {
  // A I U E O
  "あああああ", // A (vowel)
  // ⋮
  "ざじずぜぞ", // Z
  [ROW_EXTRA_CH] = "？ち？？？",
  [ROW_EXTRA_SH] = "？し？？？",
};

With this we can type shi and chi to output し and ち.

kya kyu kyo

There are also cases where 2 letters map to 2 chars. For example, ja is two kana chars: じゃ (じji + small やya).

Similarly, ju is じゅ and jo is じょ. This class of sounds is called yōon, where a syllable ending in i bends into a ya, yu, or yo sound.

These get a special symbol in the map to mark special handling. Here, let’s use fullwidth Ｙ (still 3 bytes):

static char MAP[ROW_COUNT][5*3] = {
  // A I U E O
  // ⋮
  "ＹちＹ？Ｙ", // C
  // ⋮
  "ＹじＹ？Ｙ", // J
  // ⋮
  [ROW_EXTRA_CH]    = "ＹちＹ？Ｙ",
  [ROW_EXTRA_SH]    = "ＹしＹ？Ｙ",
  [ROW_EXTRA_YOUON] = "ゃ　ゅ　ょ",
};

When a lookup returns Ｙ, we output the consonant + i, then the small ya, yu, or yo char, which is stored in an extra row.

All in all, that means: if (MAP[letter_index][vowel_index * 3] equals "Ｙ") { send(MAP[letter_index][vowel_index_for("I") * 3]); send(MAP[ROW_EXTRA_YOUON][vowel_index * 3]); }

Basic flow

Since much of the logic is encoded in the map, the keypress processing logic should be straightforward. Pressing a vowel always triggers a lookup. The lookup is based on the last pressed key (if it was a consonant).
