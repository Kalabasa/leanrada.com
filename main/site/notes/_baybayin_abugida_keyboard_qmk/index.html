Baybayin abugida input method on keyboard hardware

 01 Jan 1970 · 1 min read

I implemented an input method to write an ancient writing system called ‘Baybayin’ using a hardware keyboard via the QMK firmware.

A writing system?

Baybayin is a writing system in which a consonant-vowel sequence is generally written as one letter; it is an abugida. For example, the syllable ‘ta’ would be written as one letter, ᜆ. By default, letters have an inherent vowel which is ‘a’. To indicate a different vowel, a diacritic (kudlit) is added above or below the glyph. For example, ‘ti’ would be ᜆᜒ and ‘tu’ would be ᜆᜓ.

A ‘vowel-killer’ diacritic (virama) is also a common feature — or complication — in abugidas. In Baybayin for example, just ‘t’ would be ᜆ᜕. An example of a full word in Baybayin is ᜆᜆ᜕ᜎᜓ or ‘tatlo’, meaning the number three.

There are two variants of the virama (vowel-killer) in Baybayin. ‘t’ could be written as either ᜆ᜔ (with a small cross at the bottom) or ᜆ᜕ (a curved slash). For readability, I'm using the latter variant.

Input design

There are many ways to design an input method for this writing system on a keyboard. We could assign every possible symbol combination its own key, given enough keys. But there are 60 total possible combinations. For comparison, the Latin alphabet A-Z only has 26 letters. Input layers (hold the Shift or Fn key) could help — after all, the Latin alphabet actually has 52 total glyphs, counting both upper and lowercase.

screenshot mockup

Or we could assign only the base letters (15 keys) and 3 extra keys for diacritics. This would be a pretty efficient layout, and it’s the one used by Google’s mobile keyboard Gboard.

screenshot of Gboard

However, both of these options would require learning a whole new keyboard layout, wasting years of Latin alphabet-based muscle memory.

I wanted to type in romanised alphabet, like romaji for Japanese or pinyin for Chinese. Then the keyboard’s programmed firmware would convert keystrokes into baybayin outputs. This presents a slight challenge since one keypress would no longer directly correspond to one character.

Solution

I implemented this via QMK running on the keyboard hardware. It’s a pretty basic solution, just a bunch of if-elses and variables. Unlike romaji, I don’t need to maintain a buffer or trie or whatever data structure. It only needs to know about the last pressed key. OK, it’s a buffer of length 1.

void on_key_press(uint16_t keycode) {
  if (is_consonant(keycode)) {
    // Special case /ŋ/ (ng) is one letter ᜅ
    if (prev_keycode == KC_N && keycode == KC_G) {
      backspace(); // delete virama
      backspace(); // delete 'ᜈ' / 'n'
      send_unicode("ᜅ");
      send_unicode(VIRAMA);
    } else {
      send_unicode(get_baybayin_unicode(keycode));
      // Entering a consonant will always include a virama
      // Any vowel entered after this would need to delete the virama
      send_unicode(VIRAMA);
    }
  } else { // keycode is vowel
    if (is_consonant(prev_keycode)) {
      if (keycode == KC_A) {
        backspace(); // delete virama
      } else if (keycode == KC_I || keycode == KC_E) {
        backspace(); // delete virama
        send_unicode("ᜒ"); // combines with previous char
      } else if (keycode == KC_U || keycode == KC_O) {
        backspace(); // delete virama
        send_unicode("ᜓ"); // combines with previous char
      }
    } else { // prev_keycode is vowel
      send_unicode(get_baybayin_unicode(keycode));
    }
  }
  prev_keycode = keycode;
}

The way Unicode (Tagalog Unicode block) implemented Baybayin made this solution pretty straightforward. The vowel-modifier diacritics are combining characters, which means they can just be outputted right after the base character and the word processing application on the computer is what actually renders them as one combined character. In a way, one keypress still corresponds to one output character, except for a few special cases.

Special case ‘NG’

One special case is the letter ᜅ, representing the consonant /ŋ/. In English this sound is represented by two letters ‘ng’. This breaks the mapping of 2 Latin letters to one syllable to 1 Baybayin letter. Or 1 consonant to 1 Baybayin base letter. E.g., ‘tanga’, written as ᜆᜅ (which means ‘idiot’, pardon the example; I’m trying to minimise introducing letters). This special case is solved by a specific if clause and a couple of backtracks.

Backtracking

Backtracking is a thing because, by default, the virama must always be output after typing a consonant. When the user presses a consonant, we don’t know whether they’re going to stop typing or continue the syllable, at that point. But the base letter has an inherent vowel! Only after the next key is pressed can we be sure but then we may have to backtrack the virama. Sending a virtual Backspace signal (undistinguishable from a real Backspace keypress) fixes this.

animation of backtracking

So pressing the T key should not output just the base letter ᜆ, but the letter + virama ᜆ᜕ at once. If you actually press A, a Backspace erases the virama, leaving ᜆ, and the machine moves on to the next syllable. If you had pressed I, a Backspace erases the virama, and the I vowel diacritic ᜒ is sent, producing ᜆᜒ. Because of the inherent vowel, the backtracking design seems to be a common solution in other romanised abugida input methods as well, such as Anjal, a romanised input method for Tamil.

Why not a software IME?

Not that I often need to write Baybayin, but implementing this on the hardware makes it portable. It lives in my keyboard. I could plug my keyboard into any computer that supports arbitrary Unicode input and not have to install anything.

Generalisability to other abugidas

Baybayin is a relatively simple script. Other abugidas have vowel marks preceding the consonant. etc etc
