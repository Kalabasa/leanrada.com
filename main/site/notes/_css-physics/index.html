If you wanted to implement complex procedural animations (like physics) on the web, you’d probably go for JS-based requestAnimationFrame update-loop animations to animate each frame. But everyone knows that CSS animations (and now Web Animations API) are much smoother than frame-based JS animations.

This is because native web animations run outside the main thread, so things like heavy JS computations, DOM manipulations (like React re-renders) won’t affect it. Likewise, it won’t interfere with UI event handlers which decides your UI’s responsiveness. This makes native web animations smoother.

However, we can’t do procedural animations in CSS. CSS is declarative. Precalculating the keyframes to replay with CSS is one way to do it, but a high quality replay would normally require a heavy amount of generated CSS to download and parse.

Technique

Baking precalculated animations in CSS keyframes is nothing new I suppose, but I wanted to highlight a couple of ‘recent’ developments in CSS such as the linear() custom easing and animation composition that allow a dense expression of CSS animations — both compact representation AND high-quality replay!

First, the linear() custom ease (not to be confused with the classic linear keyword with no arguments) lets you define keyframes in the time axis.

div {
  animation: slide 2s linear(0, 0.5 60%, 0.25, 1) infinite alternate;
}
@keyframes slide {
  from {
    translate: 20px;
  }
  to {
    translate: 120px;
  }
}
div

It’s not very intuitive since we’re manually mapping values in the time domain (which is what ease functions do). To illustrate what’s happening and for comparison, we can expand the above example to classic keyframes that do the same thing:

div {
  animation: slide 2s linear infinite alternate;
}
@keyframes slide {
  0% {
    translate: 20px;
  }
  60% {
    translate: 70px;
  }
  80% {
    translate: 45px;
  }
  100% {
    translate: 120px;
  }
}
div

What linear() gives us is a compact form to define single-property animations that have multiple keyframes, just like the above.

Above is a precomputed physics simulation of a bouncy box dropped from a 50px height. The range of positions over time (min and max) becomes the from and to values. Then on every frame the position is normalized to [0,1] then encoded into linear() points.

So far we’ve only been working with one axis or degree of freedom. If we wanted a more interesting physics simulation, we’d need more spatial dimensions. This is where animation composition can come in.

Composition

animation-composition can be used to combine multiple animations so they don’t override one another.

We could add a simulteanous animation on the same translate property (in another dimension), and the resulting animation would just combine the values together:

    bounce-x 2s linear(0, 1, 0.445) infinite,

Again, this is all possible with classic keyframes, but that would require explicitly writing both coordinates in every frame. In animations where x and y are mostly independent, that is highly inefficient.

Reuse

Multiple elements can reuse the same @keyframes declarations. Since the only purpose of @keyframes now is to define the range of values, we can get the union of ranges over all elements so all elements can work within the same animation range. Individual animations are still encoded in the respective linear().

  animation:
    bounce-x 2s linear(0, 1, 0.84) infinite,
    bounce-y 2s linear(0, 0.009, 0.028, 0.056, 0.094, 0.141, 0.197, 0.263, 0.338, 0.422, 0.516, 0.619, 0.731, 0.853, 0.984, 0.906, 0.81, 0.723, 0.646, 0.578, 0.52, 0.47, 0.43, 0.4, 0.379, 0.367, 0.365, 0.372, 0.388, 0.414, 0.449, 0.494, 0.548, 0.611, 0.684, 0.766, 0.857, 0.958, 0.949, 0.876, 0.812, 0.757, 0.712, 0.677, 0.65, 0.633, 0.626, 0.627, 0.638, 0.659, 0.689, 0.728, 0.777, 0.835, 0.902, 0.979, 0.951, 0.896, 0.85, 0.814, 0.787, 0.769, 0.76, 0.762, 0.772, 0.792, 0.821, 0.859, 0.907, 0.965, 0.977, 0.936, 0.905, 0.883, 0.87, 0.867, 0.874, 0.889, 0.914, 0.949, 0.992) infinite;

 Notice how box B starts from the right, even though @keyframes pos-x is from 0px to 100px. The key is that the pos-x declaration just defines a range where boxes can be in. The actual motion is in linear() defined relative to the range, and indeed box B starts from 1 (meaning the range’s max value) going to 0 (min value).

The ability to reuse the same @keyframes declarations for all elements is another CSS efficiency win. We only need to name the specific CSS property / dimension a constant number of times, and the actual motion data is defined separately as pure numbers.

Oh, right. Baking the motion data. It depends on what your animation is, really. If it’s a simulation, then record the state of each object in each step. Only record the state with corresponding CSS property (or design your simulation state for CSSability in the first place).

After recording, you need to encode it. First, you need the ranges for the @keyframe property declaration. For each $property, find the min and max values over the whole animation and use that in @keyframe $property { from{ $property:$min } to{ $property:$max } }

Then you can encode the linear() values. Remember, one CSS animation, one linear() per property! For every sample, normalize each property’s value against the range you got from earlier to [0,1].

An optimisation could be added such that you skip writing samples that are too similar to the previous sample. Let linear() do its actual job of linearly interpolating your values. Note that skipping samples would break the property that each sample is in regular intervals, so you’d also need to add the progress percentage coordinates where necessary.

If your animation is more of the hand-authored type, then you’re just mapping keyframes. Any easing / motion curves from source material has to be ‘rasterised’ though, because we can only do linear interpolation with linear().

Alternatives considered

WAAPI. Web Animations API (WAAPI) is basically a JS API for creating CSS animations. It’s much better than dynamically constructing <style> tags. So I lied when I said JS-based animations can’t achieve native speeds (actually I didn’t, I specifically called out requestAnimationFrame only!).

  • WAAPI is used by most animation frameworks nowadays such as [Framer] Motion. They have a great article explaining JS-based vs native animations.
  • WAAPI is not an alternative per se. You can bake the simulation and replay it in either CSS or WAAPI, and get native speeds on dynamic/procedural animations either way.
