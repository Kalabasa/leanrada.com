Multilingual Philippine music

The project name Wikaraoke comes from wika (language) and karaoke (a sing-along thing). Filipinos love karaoke. Not me though, but I do love languages.

The Philippines has over 120 languages — Tagalog, Cebuano, Ilokano, Hiligaynon, Kapampangan, and so many more. My native tongue is Tagalog and I’ve only had little exposure to Kapampangan, Bikol, and Cebuano.

Even though I don’t understand most of the words in these Philippine languages, music in these languages can still resonate. And other people must feel that way too, based on the fact that songs in these languages still reach widespread popularity in the Philippines, sometimes even topping the charts.

Wikaraoke is a map-based lyric visualizer for multilingual Philippine music. It’s like karaoke, but overlaid on top of a map, highlighting the main regions where languages in a song are spoken.

Core feature

Wikaraoke features a curated set of multilingual songs. When you choose a song, it starts playing using an embedded YouTube player, which saves me the effort and legal trouble of hosting the audio files themselves.

Lyrics would then appear on the map in sync with the music from the YouTube player. Each line is associated with a language. The line is shown beside the corresponding region which lights up.

(image lyric with region lighting up)

Manually annotating the lyrics with language information has been one of the most time-consuming parts of making this. Because I’m not very familiar with any of the Philippine languages besides my own, it took quite some research to accurately annotate each line with the language it’s in.

The other tedious part is fine-tuning the timings of each line so the lyrics on screen are in time with the singing in the audio. Good timing is essential, and it complements the audio visualisation.

Audio visualisation

The visualisation reacts to the audio, not just the timed textual lyrics. It lights up and moves with the beat.

(video of audio viz)

I said I didn’t actually host the audio files (illegal), but I did host analysis data derived from the audio. This is necessary for an audio-reactive visualisation.

I wrote a Python script to analyse each of the YouTube videos’ audio tracks and compile a list of interesting aural ‘events’. These are basically instructions for the visualisation for when to react and by how much.

(code of events json)

This analysis was done offline and the resulting analysis data is saved and hosted on the website.

It’s somewhat an inefficient encoding, but it works. And that is how the visualisation reacted to the music without actually having access to the audio waveform itself.

Publishing

I realised that this isn’t really a very interactive kind of application. Once you start playing, no interaction is required.

The visualisation could be published as a prerecorded video file and enjoyed by others without having to run the webapp itself.

I think posting the lyric visualisation videos on YouTube or some other social media would be part of the products (‘deliverables’) of this project. It’s not just the webapp itself.
